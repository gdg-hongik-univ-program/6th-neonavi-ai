# 네비게이션(실시간 GPS) 기술 조사 — 웹 반응형 기준

> 작성: 2026-07-11 · 대상: FE(최서윤)·기획 공유용
> 결론 한 줄: **웹에서 "티맵처럼 부드럽게 움직이는 주행 화면"은 만들 수 있으나, "티맵 같은 풀 내비(리라우팅·음성)"는 직접 구현 부담이 커서 범위 밖. → Lv2 목표, 시간 빡세면 Lv1로 안전 하강.**

## 배경
너네비의 핵심 차별점은 **성향 맞춤 경로 추천(AI)** 이지 풀 내비 주행이 아니다.
따라서 주행 화면은 "데모에서 자연스럽게 움직여 보이는 수준"이면 충분하다.

---

## 1. 웹 실시간 위치 추적 자체는 표준 기능 (난이도: 낮음)
- 브라우저 내장 **Geolocation API `watchPosition()`** 만으로 실시간 위치 스트림 확보. 별도 유료 SDK 불필요.
- 주행용은 `enableHighAccuracy: true` 필수 (폰 GPS 사용 → 배터리↑, 갱신 약간 느림).
- **HTTPS 필수** (localhost 예외). Kakao/Naver/Google 지도 JS SDK 어느 것과도 조합 가능.

## 2. "부드럽게 움직이나?" — 핵심
원시 GPS는 **1~수 초 간격 + 좌표 튐**이 있어 그대로 찍으면 뚝뚝 끊긴다.
티맵/네이버가 매끄러운 건 GPS가 좋아서가 아니라 아래 3가지를 하기 때문:

| 기법 | 하는 일 | 웹 구현 |
|---|---|---|
| 보간(interpolation) | GPS 두 점 사이를 프레임마다 채움 | **Turf.js** + `requestAnimationFrame` |
| 맵매칭(route snapping) | 튄 좌표를 경로선 위로 붙임 | 직접 구현 or OSRM/Valhalla match |
| 카메라 추적 | 지도가 내 위치 따라 이동·회전 | Kakao `panTo()` / MapLibre `easeTo()` |

→ 웹에서도 "부드러운 이동" 재현 가능하나, 공짜가 아니라 보간+카메라 추적을 직접 짜야 함. **난이도 중.**

## 3. 진짜 turn-by-turn은 별개 문제
위치 추적 ≠ 내비게이션 엔진. "300m 앞 우회전" 하려면 별도 스택 필요:
- **Valhalla / OSRM** (오픈소스 라우팅) → 경로 + maneuver(회전 지시)
- **MapLibre GL Directions** → 웹 지도에 경로선·안내 표시하는 JS 컨트롤
- **MapLibre Navigation SDK** → 리라우팅·음성까지 되나 **Android/iOS 전용, 웹판 없음**
- **Tmap API** → 웹(JS)도 지원하나 지도표시·경로데이터 위주, 실제 턴바이턴 UI 엔진은 앱 SDK 중심

## 4. 웹의 한계 (기획서에 명시할 것)
1. **화면 꺼지면 GPS 중단** — 프라이버시 정책상 백그라운드 탭/화면 off면 `watchPosition` 멈춤. → **Screen Wake Lock API**로 화면 계속 켜두기 필요.
2. **정확도·갱신 주기**가 네이티브 앱보다 열세 (터널·고층 사이).
3. **리라우팅·맵매칭 알고리즘 직접 구현** 부담 (웹용 턴바이턴 완제품 SDK 없음).
4. 음성 안내는 **Web Speech API**로 가능하나 정교함 낮음.

---

## 5. 구현 난이도 3단계

### Lv1 (MVP · 안전선)
- 추천 경로를 폴리라인으로 그리고, `watchPosition`+Turf 보간으로 현위치 마커를 **부드럽게 추적**.
- 회전 안내는 **텍스트 스텝 리스트** 수준.
- 난이도 **중**. 데모에서 "움직이는 내비"처럼 보이기 충분.

### Lv2 (목표) — 회전 안내 카드 + 남은거리
- **회전 데이터는 이미 공짜로 옴**: Lv1에서 경로 받을 때 호출하는 Kakao/Tmap Directions 응답에 턴바이턴 안내가 포함됨.
  - Kakao → `guides` 배열 (회전 좌표 + 안내 텍스트 + 구간거리)
  - Tmap → `features`에 회전 안내 포인트
  - → **Valhalla/OSRM 따로 세울 필요 없음.** 파싱만 하면 됨.
- **새로 짜는 것은 딱 하나**: "현위치 기준 다음 회전까지 남은거리" 실시간 계산 (맵매칭 lite). Turf 함수 3개면 끝:

```js
// route: 경로 폴리라인, pos: 현재 좌표, nextTurn: 다음 회전 지점
const snapped   = turf.nearestPointOnLine(route, pos);       // 현위치를 경로선에 투영
const remaining = turf.lineSlice(snapped, nextTurn, route);
const dist      = turf.length(remaining, {units: 'meters'}); // 다음 회전까지 남은거리
// dist가 임계값 아래로 내려가면 다음 스텝으로 넘김
```

- Lv1 → Lv2 델타:

| 작업 | 난이도 |
|---|---|
| 경로 응답에서 회전 스텝 파싱 | 낮음 (데이터 이미 있음) |
| Turf로 다음 회전까지 남은거리 계산 | 중 (함수 몇 개) |
| 회전 안내 카드 UI + 스텝 자동 넘김 | 낮음~중 |

- FE 입장에서 **Lv1에 2~3일치 얹는 수준**, 새 스택 도입 아님. 난이도 **중**.

### Lv3 (비권장 · 범위 초과)
- **경로 이탈 재탐색(리라우팅)** — 상태관리·API 재호출·디바운싱 얽혀 복잡도 급증.
- 정밀 맵매칭(터널/도심 GPS 튐 보정), 음성 타이밍.
- 난이도 **상**. 우리 프로젝트 핵심 가치와 무관 → 하지 않음.

---

## 6. 결론 / 팀 합의사항
- 기존 방향("Geolocation 경량, 풀 턴바이턴 안 함")이 정확했고 본 조사가 근거로 뒷받침.
- **Lv2를 목표**로 하되, 시간 빡세면 Lv1으로 안전 하강.
- FE와 공유할 두 가지 제약: (1) 부드러움 = **보간 필요**, (2) 주행 중 화면 유지 = **Wake Lock 필요**.
- **리라우팅(Lv3)은 건드리지 않는다.**
