# 너네비 AI 파트 — 구현 계획 (안중현)

> 작성: 2026-07-11 · 담당: 안중현(AI/모델) · 순서(의존성) 기준, 날짜 미고정
> 전략: **방안 B를 먼저 완성해 서비스를 돌리고, 남는 시간에 방안 A(Two-Tower)에 집중.** 언제 끊겨도 B로 데모 가능(리스크 헷지).

---

## 확정 전제
- 후보 경로: Kakao 길찾기 `alternatives=true`로 대안 경로 여러 개 확보. 부족 시 옵션(최단/무료우선/교통최적) 바꿔 다중 호출로 pool 확대.
- 성향 축: Comfort / Sports / Eco (각 축이 선호하는 경로특성 방향 명시).
- 평가: **정식 20~30명 인간 선호 설문**, **자기선호형**(응답자 본인 선호 기준). 페르소나 종속 설문/테스트는 안 함(팀 우선순위 낮음).
- 컴퓨팅: 로컬 5080 GPU + Colab 가용.

---

## 단계별 계획 (순서 기준)

### Phase 0. 전제 고정 & 인터페이스 계약  *(여기서 막히면 전부 막힘)*
1. **후보 경로 확보 방식 확정** — `alternatives=true` + (부족 시) 옵션별 다중 호출.
2. **경로 응답 스키마 파악** → 내부 `CandidateRoute` 정의: `{polyline 좌표, 거리, 예상시간, 통행료, 회전스텝}`.
3. **`recommend_routes(user_profile, candidate_routes)` I/O 계약 확정** → 백엔드가 시그니처만 믿고 붙임.
4. **성향 축 정의 확정** — 예: Comfort=곡률↓·급경사↓, Sports=시간↓, Eco=연비↑·통행료↓.

> 산출: 인터페이스 문서 1장. → 이 시점부터 FE/BE와 완전 병렬 가능.

### Phase 1. Feature Engineering ⭐  *(A·B 공통 입력 — 최우선)*
경로 좌표 → **특성 벡터 f**.
- [x] 곡률 (`curvature.py`, Menger — 완료)
- [ ] 경사 (`elevation.py` — Open Topo Data DEM, **캐싱/배치 필수**)
- [ ] 연비/유류비 (거리+경사+도로유형 추정 또는 Naver 응답)
- [ ] 통행료 (경로 응답 or 도로공사 데이터)
- [ ] 도로유형·신호등 수 (OSM/공공데이터, 버퍼 spatial join)
- [ ] 정규화·표준화 → 후보 간 비교 가능한 스케일

> ⚠️ 임세희(데이터)님과 공공데이터 수집 구간 겹침 → Phase 0에서 역할 분담.
> 산출: `경로 리스트 → 특성벡터 리스트` 함수.

### Phase 2. 방안 B — 무학습 추천  *(먼저 서비스 완성)*
1. **성향→가중치 w 매핑**: 규칙/퍼지 or AHP로 `프로필 → w 벡터`.
2. **스코어링**: `score = w · f` + 거리 페널티(성향 vs 거리 trade-off).
3. **랭킹 + 추천 이유 생성**: "곡률 낮고 급경사 적어 편안한 경로" 식 설명.
4. **`recommend_routes` B버전 구현** → 백엔드 연결 → **E2E 데모 가능 달성.**
5. **조기 sanity 유닛테스트** 포함 (예: 노약자 동반 → 급경사·급커브 회피). GIGO 조기 검출.

> 🎯 여기까지가 "서비스가 돌아가는" 1차 완성선. 데모 최소 목표.

### Phase 3. 평가셋 구축 & 설문 착수
- 시나리오 N개(프로필 + 경로 2~3개) → **구글폼 설계** (**자기선호형**).
- **정식 20~30명** 수집 → 다수결 → **일치율(agreement) 지표**.
- **Phase 2 완료 직후 병렬 배포** (돌려두고 A 진행).

### Phase 4. 방안 A — 약지도 라벨 합성
1. **labeling function 확장** (`labeling.py`, MDSI·Sato 근거).
2. **Snorkel LabelModel**로 충돌 정리 → 확률 라벨.
3. **합성 사용자 프로필 생성기**(인구통계 분포 샘플링) → 확률 라벨 부여.

### Phase 5. 방안 A — Two-Tower 학습
1. 학습쌍: `(프로필, 경로특성, 선호라벨)` → **pairwise ranking** 데이터.
2. **User Tower(MLP) + Route Tower** → `score = w · f`.
3. 랭킹 loss(BPR/pairwise) 학습·검증(`train.py`). 로컬 5080 or Colab.
4. 체크포인트 저장 → `recommend_routes`를 A버전으로 스왑 (**B는 fallback 유지**).

### Phase 6. 비교 평가 & 발표 마무리
- **B vs A**를 인간 선호 일치율로 비교.
- 추천 이유(설명) 정교화, 발표용 지표/그래프 정리.

### 핵심 의존성
```
Phase 0 (인터페이스) ─> Phase 1 (Feature Eng) ─┬─> Phase 2 (B, 서비스 완성) ─> Phase 3 (설문, 병렬)
                                               └────────────────────────────> Phase 4 (라벨) ─> Phase 5 (Two-Tower) ─> Phase 6 (비교)
```
- **Phase 1이 병목**이자 최우선. 설문(Phase 3)은 느리니 B 완성 직후 **병렬로 미리 배포.**
- A(Phase 4~5) 못 끝내도 서비스는 B로 시연 가능.

## 리스크 관리

### 🔴 Critical — 핵심 전제를 흔드는 것

**R1. "A가 B를 못 이긴다" — 구조적 순환** *(팀 공감함)*
규칙 → 합성 라벨 → Two-Tower가 그 라벨을 학습. 모델의 정답이 규칙에서 나오므로 **A의 성능 상한 = B의 규칙 품질**. "A가 규칙보다 정확하다"는 주장은 논리적으로 약함(둘 다 같은 규칙을 측정).
- **대응**: A의 가치를 "규칙을 이긴다"가 아니라 **① 미정의 프로필 조합 일반화 ② 특성 간 상호작용 학습 ③ 부드러운 임베딩 스코어**로 프레이밍. 발표에서 "정확도↑" 주장 금지.

**R2. 후보 경로가 실제론 잘 안 갈린다** *(팀 공감함)*
`alternatives` 2~3개가 대개 서로 매우 유사 → Comfort/Sports/Eco가 같은 경로를 골라 **차별점이 안 보일** 위험. 옵션 다중 호출도 상관관계 높음.
- **대응**: (a) 경로가 실제로 갈리는 데모 O-D 선별(산길 vs 고속도로) — 체리피킹임을 정직히 밝힘. (b) 후보가 안 갈리면 "동일/추천 안 함" 처리 로직.

**R3. 설문 검증 타당성** *(→ 자기선호형으로 결정, 페르소나 비종속)*
페르소나 종속 설문/테스트는 안 하기로 함(우선순위 낮음). 잔여 리스크:
- **응답자 편중**: 응답자가 젊은 층 위주면 평가가 그 세그먼트 위주로만 유효 → "젊은 사용자 대상 검증"으로 범위를 정직히 한정.
- **제시 방식 타당성**: 정적 지도 선으로 "편안함"을 판단하기 어려움 → 경로 특성 요약(곡률/경사/시간 등)을 함께 제시해 판단 근거 보강.

### 🟡 Significant — 품질/설계 리스크

**R4. Feature Engineering GIGO(그리고 병목)**
연비 추정은 그 자체가 모델링 문제, 경사는 DEM 호출량·rate limit, 신호등은 공공데이터 커버리지 편차. 특성 절반이 노이즈면 B·A 동반 오염.
- **대응**: "신뢰 가능한 3개"에 집중, 안 되는 특성은 과감히 제외. 경사는 캐싱/배치.

**R5. Two-Tower 과설계 가능성**
Two-Tower는 큰 아이템 카탈로그+상호작용 데이터에서 유리. 여긴 쿼리당 경로 2~3개, 실피드백 0, 특성 수작업 → 사실상 화려한 가중합. "왜 Two-Tower?"에 취약.
- **대응**: **pairwise learning-to-rank(작은 MLP/로지스틱)를 기본선**으로. Two-Tower는 아키텍처 근거가 설 때만 채택하고 선택 이유 준비.

**R6. 윤리/편향 — 성별·나이 고정관념**
`lf_young_male → SPORTS`는 성별+나이 고정관념을 각인 → "젊은 남성=난폭?" 지적 소지.
- **대응**: 개별 판단 아닌 집단 사전확률, 사용자 오버라이드 가능, 민감속성 가중치 축소 옵션. 최악 시 성별 피처 제거 고려.

**R7. 1인 AI 스코프 — A는 미완 가능성 높음**
Feature Eng(5종)+B+설문+Snorkel+Two-Tower+비교를 혼자 파트타임 → Phase 4~5 미완 확률 큼.
- **대응**: "완벽"의 기대치를 **B + 견고한 Feature Eng + 설문**으로 설정. A는 상방(bonus).

### 🟢 Minor / 운영
- **R8. 지도 API "잠정"** → Kakao/Naver 확정을 **Phase 1 전에** 못박기. 뒤집히면 특성 추출·계약 churn.
- **R9. 조기 sanity 지표 부재** → 손라벨 유닛테스트로 B 조기 검증(Phase 2 포함).
- **R10. B의 LLM zero-shot** → 비용·지연·비결정성. 실험용으로만, 메인 경로에선 제외.

- [ ] R2/R8: 지도 API 확정 + 후보 경로가 실제 갈리는 O-D 몇 개로 사전 검증
- [ ] R3: 설문 = 자기선호형 확정, 응답자 편중 한계 문서화, 특성 요약 함께 제시
- [ ] R4: Feature Eng "신뢰 3개"에 집중, 나머지 후순위
- [ ] R5: pairwise LTR 기본선, Two-Tower는 근거 있을 때만
- [ ] R9: 조기 sanity 유닛테스트를 Phase 2에 포함

> 가장 아픈 건 R1(순환)·R2(경로 안 갈림) — 코드로 못 없애고 프레이밍/데모 설계로 관리. 나머지는 실행 리스크로 관리 가능.
